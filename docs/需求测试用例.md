| 执行状态 | **全部「未执行」**。本表是测试设计产出，不含任何执行结果或编造的通过率 |

> **为什么单独做这份映射**
> 需求文档回答「要做什么」，测试用例回答「怎么证明它做对了」。两者靠编号双向绑定，才能做**确定性覆盖检查**：机器可读地判断「有没有需求没被用例覆盖」「有没有用例找不到需求来源」。这也是「需求 → 测试用例 AI 助手」类工具必须保留人工确认与覆盖校验环节的原因——LLM 生成用例容易漏边界，但漏没漏可以被程序精确判定。

---

## 1. 编号与检查规则

| 项 | 规则 |
|---|---|
| 需求编号 | `R-{模块}-{序号}`，模块 A 建档 / B 打卡 / C 算法 / D 体重 / E 数据 / F 激励与内容 / G 分享 / H 数据与隐私 |
| 用例编号 | `TC-{模块}-{三位序号}` |
| 追溯字段 | 每条用例必须填写 `关联需求`，值为 1 个或多个 `R-xxx` |
| 覆盖判据 | `需求集合 − 用例引用集合 = ∅` 且 `用例引用集合 − 需求集合 = ∅` |
| 覆盖粒度 | **需求编号级**覆盖；不等于路径覆盖 / 分支覆盖，后者需另做代码级白盒测试 |
| 优先级 | P0 发布阻断 / P1 重要 / P2 一般 |

用例类型：`功能` 正常流、`边界` 边界值与等价类、`异常` 失败与降级、`权限` 隔离与隐私、`兼容` 机型与性能。

### 4.2 可复用的机器校验思路

```
demands  = 解析 01-PRD.md 第 4 节表格，正则提取 /R-[A-H]\d{2}/g → 集合 D
refs     = 解析本文「关联需求」列，正则提取同样格式 → 集合 C
```
