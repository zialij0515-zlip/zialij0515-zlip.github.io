## 1. 为什么需要这份文档

PRD 第 1.4 节把「用户能坚持记录」写成产品假设，但假设必须可证伪。当前工程只有业务数据（打卡、体重），**没有行为数据**：能算出「谁打了卡」，算不出「多少人在建档后放弃」「哪一步流失最多」「热量估算到底准不准被人接受」。这份文档把「上线后要回答的问题」翻译成可采集、可计算、口径明确的指标。

设计原则：**先定问题，再定指标，最后定埋点**；能由业务数据算出来的，绝不重复埋点；能不采集的敏感信息，一律不采集。

## 2. 指标分层

### 2.1 北极星指标

**周有效打卡用户数（WACU, Weekly Active Check-in Users）**
> 自然周（周一 00:00 – 周日 23:59:59，东八区）内，**至少 1 天完成 ≥1 项打卡**的去重用户数。

| 判断 | 说明 |
|---|---|
| 为什么不是 DAU | 打开但不记录不产生价值，DAU 会把「误触启动」算成成功 |
| 为什么不是打卡总次数 | 次数鼓励刷量，与「低压力坚持」的产品原则冲突 |
| 为什么用「周」 | 减脂是周级节奏；日级波动受工作日/周末影响大，个人工具样本量小 |
| 为什么是「≥1 项」 | 首次使用者只打一项也应计入，避免门槛过高掩盖激活问题 |

用户侧价值代理指标：**连续打卡天数**（`home.js computeStreak` 已实现，产品内可见）。它不适合作为公司级北极星（不可跨用户加总），但适合作为**用户个体获得价值**的信号，用于分层与同期群分析。

### 2.2 输入指标（驱动北极星）

| 指标 | 定义 | 想回答的问题 |
|---|---|---|
| 建档完成率 | 完成建档用户 / 进入建档页用户 | 首次门槛是否过高 |
| 首次打卡转化率 | 建档后当日完成 ≥1 项打卡 / 建档完成用户 | 建档后是否知道「下一步做什么」 |
| 日均打卡项数 | 当日打卡 `type` 去重数之和 / 有效打卡用户日 | 用户是浅尝还是形成完整记录习惯 |
| 热量估算命中率 | `matched=true` 的餐食打卡 / 全部餐食打卡 | 食物库是否够用，决定要不要继续扩充 |
| 连续打卡中位数 | 用户级连续天数的中位数（非均值，抗长尾） | 典型用户能坚持多久 |
| 提醒触达有效率 | 提醒后当日完成打卡 / 提醒曝光 | 应用内提醒是否真的有用 |

### 2.3 结果指标

| 指标 | 定义 | 注意 |
|---|---|---|
| 目标达成率 | 达到 `当前体重 ≤ 目标体重` 的用户 / 建档用户 | 周期长、样本小，只做趋势观察，不做因果宣称 |
| 体重变化分布 | 建档后第 N 周体重变化的**分位数**（P25/P50/P75） | 只上报聚合分位，不上报个体数值；避免引出医疗结论 |
| 海报生成率 | 生成海报用户 / 达标用户 | 达标激励闭环是否被使用 |
| 分享率 | 触发分享用户 / 当日有打卡用户 | 分享是否构成自然传播入口 |

### 2.4 护栏指标（防止「增长」以牺牲体验为代价）

| 指标 | 阈值建议 | 为什么 |
|---|---|---|
| 云端同步失败率 | 需持续监控，`sync_fail` / `checkin_save` | 本地降级虽不丢数据，但失败率高说明跨设备体验已破损 |
| 打卡重复写入率 | 同 `date+type` 云端文档数 > 1 的占比 | 对应 RISK-03，直接影响指标可信度 |
| 崩溃 / 白屏 / 永久 loading | 发布阻断级 = 0 | 见开发计划第 5.3 节 |
| 订阅消息打扰信号 | 关闭提醒开关率、授权拒绝率 | 个人主体一次性订阅配额有限，过度索取授权会伤体验 |
| 估算值误导风险 | 页面是否始终带「估算 / 仅供参考」 | 合规护栏，用**检查项**而非数值指标 |

## 3. 主漏斗

```
① 小程序启动 app_launch
        ↓ 流失点 1：启动后未进建档 / 中途退出
② 建档页曝光 onboarding_view
        ↓ 流失点 2：字段太多 / 校验报错
③ 建档完成 onboarding_complete
        ↓ 流失点 3：建档后不知道下一步
④ 首次打卡 checkin_save（当日 ≥1 项）
        ↓ 流失点 4：文字估算不准 / 保存失败
⑤ 当日完整记录（≥3 项打卡）
        ↓ 流失点 5：次日遗忘
⑥ D7 留存（建档后第 7 天仍有打卡）
```

**每一步的口径必须固定**：分母是上一步的去重用户数；同期群按**建档日所在自然周**分组；跨步骤窗口为建档后 0 / 1 / 7 天。

留存定义（避免常见歧义）：
| 名称 | 定义 |
|---|---|
| D1 打卡留存 | 建档后第 1 个自然日完成 ≥1 项打卡的用户 / 建档用户 |
| D7 打卡留存 | 建档后第 7 个自然日完成 ≥1 项打卡的用户 / 建档用户 |
| D7 窗口留存 | 建档后 1–7 天内**任意一天**有打卡的用户 / 建档用户 |

三者不可混用。默认报表用 **D7 窗口留存**，并在图表标题写明口径。

## 4. 指标字典

| 指标名 | 分子 / 分母 | 数据源 | 更新频率 | 口径注意 |
|---|---|---|---|---|
| WACU | 周内有效打卡去重用户 / — | `checkins` | 每日 | 周一为周起点；去重键 = 用户 + 自然周 |
| 建档完成率 | `onboarding_complete` 去重用户 / `onboarding_view` 去重用户 | 事件 | 每日 | 编辑模式 `?from=profile` 不计入分母 |
| 首次打卡转化率 | 建档当日有打卡用户 / 建档完成用户 | `users` + `checkins` | 每日 | 「当日」用东八区日期 |
| 日均打卡项数 | `count(distinct date+type)` / 有效打卡用户日 | `checkins` | 每日 | 同日同类型去重（对应 `store.addCheckin`） |
| 热量估算命中率 | `kcalItems` 中 `name != '默认估算'` 的餐食打卡 / 全部餐食打卡 | `checkins.kcalItems` | 每周 | 运动打卡不在分母内；否定词「没吃」单独剔除 |
| 连续打卡中位数 | 用户级 `computeStreak` 的中位数 | `checkins` | 每周 | 用中位数不用均值；今天未打卡从昨天起算 |
| 云端同步失败率 | `sync_fail` 事件数 / `checkin_save` 事件数 | 事件 | 每日 | 本地降级成功也计为失败事件，用于监控 |
| 目标达成率 | 达标用户 / 建档用户 | `body_records` + `users` | 每周 | 达标判定 `weight <= targetWeight`，不含医疗判断 |
| 分享率 | `share_tap` 去重用户 / 当日有打卡去重用户 | 事件 + `checkins` | 每周 | 灰置态点击不计入（`onShareDisabledTap` 单独统计） |

## 5. 事件埋点表

**命名规则**：`{模块}_{动作}`，小写下划线；所有事件由上报层自动附带 `user_pseudo_id`（openid 哈希）、`event_id`（幂等键）、`ts`、`app_version`、`platform`，业务侧不重复传。

| 事件名 | 触发时机 | 关键参数 | 来源 | 用途 |
|---|---|---|---|---|
| `app_launch` | 冷启动完成 | `scene`（微信场景值）、`is_new` | `app.js` | 漏斗入口、渠道 |
| `onboarding_view` | 建档页 `onLoad` | `from`（`first` / `profile`） | `onboarding` | 分母；编辑态可排除 |
| `onboarding_complete` | 建档提交成功 | `duration_ms`、`hint_shown`（是否出现斤提示） | `onboarding` | 建档完成率、表单耗时 |
| `checkin_view` | 记录页 `loadType` 完成 | `type`、`entry`（`home_card` / `tab_auto`） | `record` | 自动跳转是否把用户带到正确 tab |
| `checkin_save` | 本地保存成功（**先于云端同步**） | `type`、`kcal_source`（`food_db` / `fallback` / `sport`）、`matched`、`item_count`、`image_count`、`has_mood` | `record` | 核心漏斗、命中率 |
| `calorie_estimate` | 文字输入触发实时估算（防抖后） | `type`、`matched`、`item_count` | `record` | 估算命中率、食物库扩充优先级 |
| `weight_save` | 体重保存成功 | `hint_shown`、`converted`（布尔） | `record` | 斤→kg 提示有效性；**不传体重数值** |
| `data_view` | 数据页 `onShow` | `metric`、`range`、`has_data` | `data` | 哪些曲线被真正使用 |
| `poster_view` | 海报页 `onLoad` | `reached` | `poster` | 达标闭环 |
| `poster_save` | 保存相册成功 | `reached` | `poster` | 分享意愿代理 |
| `share_tap` | 点绿色分享按钮 | `image_ready`（缓存图是否已生成） | `home` | 分享率、图生成成功率 |
| `share_result` | 转发回调 / promise 结束 | `with_image`、`fallback`（是否降级纯文字） | `home` | 对应 RISK-07 |
| `share_disabled_tap` | 点灰置分享按钮 | — | `home` | 判断灰置是否造成困惑（若量大应改引导文案） |
| `diary_save` | 日记保存成功 | `is_edit` | `home` | 内容功能使用度 |
| `remind_show` | 应用内提醒弹层出现 | `channel`（`modal` / `red_dot`） | `home` | 提醒曝光分母 |
| `remind_click` | 点「去记录」 | — | `home` | 提醒点击率 |
| `subscribe_result` | 订阅授权回调 | `granted`、`reason`（拒绝时） | `home` / `profile` | 打扰护栏 |
| `push_sent` | 云函数发送成功 | `today`、`batch` | `slim-reminder` | 触达量；**批量上报，不含 openid 明文** |
| `sync_fail` | 任一云端读写/上传失败 | `stage`（`upload` / `checkin` / `body` / `diary` / `pull`）、`reason_code` | `utils/cloud.js` | 护栏指标 |

### 5.1 隐私约束（硬性）

| 不采集 | 原因 |
|---|---|
| `note` 文字原文、`diary` 正文 | 可能含健康、身份、位置等自由文本，属过度采集 |
| 图片 fileID / URL | 用户私人照片，业务集合已存，分析层无需副本 |
| 体重、BMI、体脂率**具体数值** | 敏感个人健康信息；结果指标只用聚合分位数 |
| 昵称、头像、手机号 | 与度量目标无关；v1 本就不绑手机号 |
| openid 明文 | 上报层统一转为不可逆哈希 `user_pseudo_id` |
| AppSecret / 模板 ID | 凭据不进任何日志与事件 |

数据最小化依据：本方案只回答「功能是否被使用、在哪流失、是否稳定」，上述问题均可在不接触内容原文的情况下回答。若未来要做「食物识别准确率」等需要文本的分析，须单独走用户授权与脱敏流程，不在此方案内。

### 5.2 事件幂等

- `checkin_save` 用 `user_pseudo_id + date + type + event_id` 去重；对应本地 `store.addCheckin` 的 `date+type` 覆盖语义。
- `onboarding_complete` 每用户仅一次有效（编辑态不计）。
- `push_sent` 由云函数按批次上报一次，不在用户循环里逐条上报。

## 6. 与现有数据模型的映射

| 分析需求 | 现有数据能否支撑 | 说明 |
|---|---|---|
| WACU / 连续打卡 / 日均打卡项数 | ✅ 能 | `checkins` 有 `date`、`type`、`_openid` |
| 热量估算命中率 | ✅ 能 | `checkins.kcalItems` 含 `name`，可判断是否「默认估算」 |
| 目标达成率 / 体重变化分位 | ✅ 能 | `body_records` + `users` |
| 提醒触达量 | ✅ 能 | `reminder_subs` + 云函数返回 `{sent, skipped, disabled}` |
| 建档漏斗 / 流失点 | ❌ 不能 | 需 `app_launch` / `onboarding_view` / `onboarding_complete` |
| 分享、海报、数据页使用度 | ❌ 不能 | 需行为事件 |
| 同步失败率 / 降级频率 | ❌ 不能 | 当前失败只写 `console.warn`，需 `sync_fail` 事件 |
| 崩溃 / 白屏 | ❌ 不能 | 需接入小程序官方错误监控或自建上报 |

**落地建议（二选一）**
- **轻量**：新增云数据库集合 `events`，`cloud.js` 包一层 `track(name, params)`，批量写入；适合个人项目，无第三方依赖。
- **标准**：接入微信官方数据分析 / 小程序「自定义分析」，行为漏斗可直接用平台报表；需按平台要求配置事件与参数。

无论哪种，`daily_summary` 集合（`slim-init` 已创建但目前未读写）都可改造成**按日预聚合表**，避免每次报表全表扫描。

## 7. 分析计划

| 序号 | 分析 | 方法 | 输出决策 |
|---|---|---|---|
| 1 | 建档主漏斗 | 按建档周做同期群，逐步算转化率 | 定位最大流失环节，优先改该步（而不是凭感觉改首页） |
| 2 | 打卡留存 | D1 / D7 / D30 同期群曲线，按建档周分组 | 判断「坚持」是否随版本迭代改善 |
| 3 | 热量估算命中率 | 按餐次、时段、是否含别名词拆分 | 命中率低的类别优先补食物库；这是数据反哺产品的闭环 |
| 4 | 提醒有效性 | 开启 vs 未开启提醒用户的次日打卡率 | **观察性对比，不能当因果**；若差异大，再设计 A/B（提醒时机/文案） |
| 5 | 自动跳转效果 | `entry=tab_auto` 与 `entry=home_card` 的保存转化率对比 | 判断 R-B05 的自动跳转是否真的降低摩擦 |
| 6 | 分享传播 | `share_result` → 新用户 `app_launch` 的场景值归因 | 判断分享是否值得继续投入 |

**A/B 测试前提**：个人项目样本量小，**先做定性观察与可用性测试，不要在小样本上跑百分比显著性检验**。等周有效打卡用户达到可比较规模后再设计实验，并预先登记主要指标与最小可检测效应，避免事后挑指标。

## 8. 数据质量与口径陷阱

| 编号 | 陷阱 | 处理 |
|---|---|---|
| DQ-01 | **UTC 日期口径**（PRD RISK-01） | 客户端 `today()` 用 `toISOString()`，北京时间 00:00–08:00 会归到前一日，直接污染所有按日指标。**取数前必须先把客户端日期统一为东八区**（云函数已有 `todayBeijing()` 可复用），否则留存、连续天数、周完成率全部不可信 |
| DQ-02 | 云端重复写入（RISK-03） | `syncCheckin` 用 `add` 而非业务键 upsert；统计前需按 `openid+date+type` 去重，同时把重复率作为护栏指标 |
| DQ-03 | 读取上限（RISK-02） | 客户端 `.get()` 未设 `limit`，报表若直接读集合可能读不全；报表侧改用分页/聚合，或先修读取 |
| DQ-04 | 本地与云端双源 | 本地 Storage 是主路径，云端可能滞后；指标以**云端业务集合**为准，并在报表中标注同步延迟 |
| DQ-05 | 预览假数据 | `data.js` 保留 `USE_FAKE_DATA` 开关（当前 `false`）；上线构建必须确认为 `false`，否则污染体重类指标 |
| DQ-06 | 分母定义漂移 | 建档完成率、留存率的分母一经确定不随版本改动；若必须改，另起指标名并保留历史口径 |
| DQ-07 | 小样本过度解读 | 单个用户占比过高时，百分比会剧烈跳动；报表同时展示绝对数，且不做显著性宣称 |

> DQ-01 是**最高优先级**：它是 PRD 静态检查发现的风险、测试用例 `SP-01` 的验证对象，也是全部指标可信度的前置条件。这条链路把「需求 → 测试 → 度量」三份文档串成了一个闭环。

## 9. 本方案不做的事

- 不做用户画像标签体系 / RFM（单用途工具，暂无商业分层需求）。
- 不采集健康数据明细做营养或医疗分析，不做跨用户体重对比。
- 不引入第三方广告或行为追踪 SDK。
- 不在未验证口径前给出任何目标值（如「留存要到 40%」）——没有基线时拍目标是伪精确。
