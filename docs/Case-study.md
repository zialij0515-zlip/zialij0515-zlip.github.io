# 轻减日记 · 项目复盘（一页纸）

> 一款个人减脂打卡微信小程序。从产品定义、原生小程序实现、微信云开发接入，到需求基线、测试设计与度量方案的完整闭环。
> 2026-09 → 2026-11 ｜ 个人独立开发 ｜ 原生微信小程序 + 云开发（云函数 / 云数据库 / 云存储）
> **本文所有陈述均可在仓库源码与 `docs/` 文档中核验；不含任何未经测量的运营数据。**

---

## 背景与问题

减脂记录工具普遍有两个劝退点：一是把「记录」做成负担（查食物库、手算卡路里），二是把体重波动做成焦虑（红字、惩罚、日目标）。我想验证一个假设：**如果把记录成本压到「写一句话」，并用中性、可解释的方式反馈数据，个人能不能自己坚持下来？**

约束同样明确：个人主体小程序、无运维、无后端团队、无推广预算，且健康类数据必须谨慎处理。

## 关键决策与取舍

> 这部分是项目里最值得讲的内容：**每个决策都有「放弃了什么」和「代价」**。

| # | 决策 | 为什么 | 放弃了什么 / 代价 |
|---|---|---|---|
| 1 | **文字描述估算热量**，不做照片识别、不建完整食物库 | 拍一张照比写一句话重；先用 171 条常见中餐 + 长词优先匹配 + 兜底估算覆盖大多数场景 | 放弃精度。代价是需要持续补库（曾因「糯玉米」漏匹配只识别出鸡蛋），且必须把「估算值·仅供参考」写进界面，不能让用户当成营养处方 |
| 2 | **本地先存成功，云端异步同步** | 弱网/云环境不可用时记录不能丢；个人项目没有重试队列 | 放弃强一致与即时跨设备。代价是云端可能滞后、同日重复 `add`（已列为 RISK-03），需要后续改业务键 upsert |
| 3 | **客户端直写 + openid 自定义安全规则**，不自建后台 | 无运维能力，云开发权限规则已足够做用户隔离；密钥只放云函数环境变量 | 放弃复杂服务端逻辑与运营后台。代价是管理员侧只能靠云开发控制台 + 一份操作指南 |
| 4 | **体脂率用 Deurenberg 估算并强制标注** | 没有体脂秤也能给出可参考的趋势指标 | 放弃「看起来专业」的精确数值。代价是必须持续克制文案，不给医疗结论；这是产品伦理取舍，不是技术取舍 |
| 5 | **提醒以应用内为主**，订阅消息为辅 | 个人主体默认只有一次性订阅，长期订阅类目拿不到，承诺「每天必推」必然失信 | 放弃稳定触达。代价是改成弹层 + tab 红点这类「用户打开才有效」的方案，并在文档里明写平台限制 |
| 6 | **斤→kg 只提示、不自动转**（阈值 > 80） | 输入 130 可能是斤也可能是真实 kg，自动 ÷2 会静默篡改身体数据 | 放弃一步到位。代价是多一次点击；但保住了「用户数据不被系统猜测覆盖」这条底线 |
| 7 | **分享按钮灰置而非隐藏** | 完全隐藏会让用户以为没有分享功能 | 放弃极简视觉。代价是要在无打卡态多一套提示文案与交互；仅做聊天转发，不做朋友圈，避免为分享而诱导 |

## 质量与验证

- 发布阻断级验收标准覆盖功能正确性、视觉与图片质量、流畅度、文案、隐私五个维度（见开发计划第 5 节）。
- 需求与用例用编号双向绑定，覆盖检查用**集合差**做确定性判定，不靠人工目测：「有需求没用例」和「有用例没需求」都能被程序检出。
- 静态阅读代码后圈定 8 个待验证风险，其中最关键的是**客户端 `toISOString()` 的 UTC 日期口径**——它在北京时间凌晨会把记录归到前一日，同时污染连续打卡、周完成率和上线后的留存指标。已把它同时写进 PRD 风险表、测试专项 `SP-01` 和指标方案 `DQ-01`，形成「需求 → 测试 → 度量」的闭环。
- 所有测试用例状态为**未执行**，不填通过率；真机、弱网、空数据、多分辨率回归仍待完成。

## 结果（诚实口径）

**已实现的客观事实**：完整可运行的小程序工程、10 个页面、5 类打卡、171 条食物库、7 个云集合、3 个云函数、4 份产品与质量文档，代码托管在 GitHub 并保留完整迭代提交历史。

**尚不能陈述的结果**：项目处于个人开发与备案通过阶段，**没有可公开的真实用户量、留存率、转化率或业务增长数据**。因此本文不写「提升了 X%」这类结论。上线后的验证口径已预先定义在 `03-指标体系与埋点设计.md`，避免事后挑指标。

## 如果重做

1. **先统一时区口径再写业务代码**——日期是几乎所有指标的公共地基，后补代价最高。
2. **埋点方案前置到开发阶段**——现在只能「设计态」，上线后无法回溯首次漏斗流失。
3. **云端写入按业务键 upsert**，从源头消除重复数据。
4. **给 171 条食物库配一组回归语料**（长词、份量词、否定词、未命中），每次补库自动跑，避免「补了玉米又漏了别的」。
5. **视觉回归自动化**：高保真原型逐页比对目前只能人工，是开发计划里明确记录的验收限制。

---

## 面试可讲的三个点

1. **「需求 → 测试用例」为什么需要 RAG + 人工确认 + 确定性覆盖检查**：这份 PRD 就是最好的语料样本，映射表就是可对照的 gold standard。LLM 负责生成候选用例，程序负责算出「哪些需求没被覆盖」，人负责判断业务语义——三者分工不能互相替代。
2. **数据最小化不是合规话术，是设计动作**：埋点方案里明确不采集文字原文、图片、体重具体值、昵称、openid 明文；健康类产品能在不碰内容的前提下回答「功能有没有被用、在哪流失」。
3. **平台约束下的产品取舍**：个人主体的订阅消息限制、小程序 `button` 默认样式、自定义转发图在部分基础库的降级……这些都不是代码 bug，而是需要在需求文档里写明边界、并设计降级路径的产品约束。
