# B 项目 PRD · 华夏基金养老业务线「自助问数助手」

> 文档定位：AI 产品经理作品集交付物。配套设计文档见 `B项目_WrenAI_华夏基金养老_方案设计.md`，语义层口径见 `B项目_语义层MDL与指标口径.md`，测试题见 `B项目_指标测试问题清单.md`。
> 技术底座：WrenAI（Canner，Apache-2.0，legacy/v1 分支的 Wren GenBI Classic），PostgreSQL + 合成数据。

---

## 1. 背景与目标

**业务痛点**：养老理财业务线的经营取数长期依赖「业务提需求 → 数据团队排期 → T+1 出数」，口径还容易混乱（例如「养老规模」到底含不含税延账户、是否只算最新快照）。业务/投研/客服同学想随时自查数据，却卡在技术门槛上。

**产品目标**：提供一个内部自助问数助手，非技术岗用自然语言提问即可获得可信的经营数据，且**同一指标在不同人嘴里口径一致**（这是和传统「裸接 LLM 写 SQL」最大的区别）。

**AI PM 定位**：我在这个项目里不是写 SQL 的人，而是**定义业务口径、治理语义层**的人。模型、向量库、SQL 生成都是工具，真正的主战场是「指标口径的设计与锁定」。

## 2. 目标用户与使用场景

| 角色 | 诉求 | 典型问题 |
|---|---|---|
| 业务运营 | 看规模/渗透率/申赎 | 「养老资产规模多少」「本月申购赎回多少」 |
| 投研 | 看收益/留存 | 「定投留存率」「整体持仓是赚是亏」 |
| 客服/投顾 | 按画像解释 | 「55 岁以上用户占比」「一线用户多少」 |

## 3. 核心能力需求

- **R1 自然语言问数**：用大白话提问，自动生成可执行的 SQL 并回数。
- **R2 指标口径治理**：6 个核心经营指标口径被锁定为视图（View），任何人问都走同一套定义。
- **R3 口径可审计**：指标定义写进语义层文件，修改需走评审，杜绝「同指标不同数」。
- **R4 行级权限（设计项）**：客服角色只能看聚合结果，不可下钻到单用户明细。

## 4. 方案概述（技术架构）

```
用户(自然语言)
   ↓
Wren UI (localhost:3000)
   ↓
Wren AI Service ── 语义层 MDL(实体/关系/指标视图/权限)
   ↓
PostgreSQL (合成数据：dim_* / fact_* 共 5 表, 约 12 万行)
```

- **LLM**：阿里百炼 Qwen（qwen-plus）—— 因 WrenAI 0.29 核心管线要求 `json_schema` 结构化输出，DeepSeek 不支持该格式、OpenAI 需充值且国内需代理，故选百炼 Qwen（同一把 Key 兼做 Embedding）。
- **Embedding**：阿里百炼 text-embedding-v3（维度 1024）。
- **数据源**：PostgreSQL（独立容器，与本机隔离），通过 `host.docker.internal` 接入 WrenAI 容器网络。

## 5. 语义层设计（最值钱的部分）

### 5.1 实体与关系
- 维表：`dim_fund`（基金，区分养老/非养老）、`dim_user`（投资者画像）
- 事实表：`fact_position`（持仓快照）、`fact_order`（申购/赎回）、`fact_dingtou`（定投计划）
- 关系：`fact_*.user_id → dim_user.user_id`；`fact_*.fund_code → dim_fund.fund_code`

### 5.2 治理视图（已部署，6 个）
| 视图名（英文，WrenAI 标识符约束） | 对应指标 | 锁定口径 |
|---|---|---|
| `m_ElderlycareAUM` | 养老资产规模 | SUM(market_value) WHERE 养老 AND 最新日期 |
| `m_penetrationRate` | 个人养老账户渗透率 | COUNT(开通)/COUNT(*) |
| `m_dingtouRate` | 定投留存率 | 进行中用户/开启定投用户 |
| `m_yieldRate` | 整体持仓收益率 | (市值-成本)/成本（最新快照） |
| `m_monthlyRate` | 月度申购/赎回 | SUM(amount) GROUP BY 月, 类型 |
| `m_Userdistribution` | 用户年龄分布 | 按年龄段分组计数 |

### 5.3 治理规则
- **口径锁定 + 版本化**：指标定义进 MDL，变更走评审。
- **行级权限**：客服角色仅聚合视图，禁明细下钻（设计项，待接入角色体系）。
- **Schema 缺口的口径降级**：原「连续定投≥3 期」与「净值年化收益率」在本 Schema 不可计算，已降为可计算代理口径（进行中占比 / 持仓收益率），并在文档中显式标注。

## 6. 关键决策记录（面试可讲）

- **为什么不用 DeepSeek 做 LLM**：实测 DeepSeek 对 `json_schema` 返回 400（仅支持 `json_object`），而 WrenAI 0.29 所有核心管线（SQL 生成、意图分类、图表等 13 处）强制使用 `json_schema`，直接用会整体失败。
- **为什么不用 OpenAI**：账号额度为 0（429），且国内容器需代理。
- **最终选型**：百炼 Qwen，一个 Key 通吃 LLM + Embedding，国内直连、零新增成本、不改动源码。

## 7. 数据方案

采用**合成数据**（方案甲）：按上述 Schema 造约 1 万模拟投资者 + 持仓/订单/定投，约 12 万行，脱敏且口径由本项目定义，演示成立。实测基准值：养老 AUM 8.73 亿、渗透率 45.15%、定投留存 70.89%、持仓收益率 7.87%、12 月申购 3112 万 / 赎回 3198 万。

## 8. 量化指标（Text2SQL 准确率）

> 由 `B项目_指标测试问题清单.md` 的 20 条用例实测回填。验收口径：SQL 生成率 / SQL 正确率 / 答案合理率（详见清单）。
> **本轮（2026-10-21）已实施 §8.5 优化并重跑，形成「治理前 → 治理后」闭环。**

### 8.1 治理前 vs 治理后 · 三率闭环
| 指标 | 治理前基线（第二轮） | 治理后实测（第三轮） | 变化 |
|---|---|---|---|
| SQL 生成率（生成 SQL / 20） | 13/20 = 65% | **20/20 = 100%** | +35pct |
| SQL 正确率（口径一致 / 20） | 4/20 = 20% | **18/20 = 90%** | +70pct |
| 答案合理率（数值合理 / 20） | 4/20 = 20% | **18/20 = 90%** | +70pct |
| 视图命中率* | 0/20 = 0% | 0/20 = 0% | 口径调整，见 §8.6 |

> *视图命中率原为设计目标（≥90%），但实测发现 WrenAI legacy/v1 的「Save as View」不进入 NL→SQL 检索，故治理机制改为 **SQL pairs 黄金示例**（见 §8.6），该指标不再适用，改为以「SQL 正确率 / 答案合理率」衡量治理效果。

### 8.2 逐题结论速览
- ✅ **完全正确（4 题）**：#4 开通账户数=4515（=渗透率分子）、#8 持仓盈亏=+6.92 亿（正收益）、#11 城市层级分布（二线最多）、#17 总用户=10000。这 4 题都是**直接走原始表、且 LLM 恰好拼对了字段/值**。
- ⚠️ **生成 SQL 但答案错误（8 题）**：#6 #9 #13 #15 #19 #20 全是**维度取值不匹配**；#12 粒度过细（按精确年龄而非年龄段）；#16 `risk_level` 是文本，用 `MAX()` 取的是字典序最大值、语义错误。
- 🔴 **直接走 GENERAL 不生成 SQL（7 题）**：#1 #2 #3 #5 #7 #10 #14，**其中 6 个治理指标题全部未命中视图**。
- 🐞 **测试脚本 bug（1 题）**：#18 SQL 逻辑正确，但对账脚本 `Decimal` 无法 JSON 序列化，已记录待修（不计入 WrenAI 失败）。

### 8.3 治理前根因分析（本项目最值钱的一页）
两类互相独立的问题，且都直指「语义层治理」的本质：

**(A) 治理视图 0% 命中 —— 视图没进语义检索**
WrenAI legacy/v1 的「Save as View」只是 UI 收藏（存进"我的查询"），**不会进入 NL→SQL 的模型检索**。实测 `listModels` 只有 5 张基础表，6 个治理视图根本不在检索候选里。所以问"养老资产规模"时系统找不到对应模型，只能 GENERAL 用大模型知识硬答（还把中文翻成英文去理解）。
→ 这是**工具边界，不是配置错**；但也说明：要真让指标治理生效，视图必须作为**一等公民建模进 MDL 语义层**（带关系、带描述、带指标定义），而不是只点"存为视图"。

**(B) SQL 生成了但答错 —— 缺维度取值映射**
13 题生成了 SQL，语法**全对**，但 8 题答案错，原因高度一致：**LLM 猜的是英文/英文式枚举值，而库里存的是中文值**：
| 列 | LLM 猜的值 | 库里真实值 |
|---|---|---|
| `fact_dingtou.status` | `active` | `进行中` |
| `dim_user.city_tier` | `first-tier` | `一线` |
| `fact_order.order_type` | `subscribe` / `redeem` | `申购` / `赎回` |
| `dim_fund.fund_type` | `%pension%` | `养老` |
| `fact_dingtou.frequency` | `周定投` / `月定投` | `周` / `月` |
→ 这正是「裸接 LLM 写 SQL」的本质缺陷，也正是语义层该补的**列级取值 / 同义词映射**。

### 8.4 这个结论反而证明了产品价值
PRD 原计划写"视图命中率≥90%"，实测 0%，**但这不是项目失败，而是把抽象需求变成了可验证的硬结论**：
1. 治理视图如果只是"存为视图"没用，必须建模进 MDL → 落地时改用更贴 legacy/v1 的 **SQL pairs 黄金示例**（§8.6）；
2. 即使走原始表，缺取值映射也会大面积答错 → 证明"语义层治理"（不只是 SQL 生成）是刚需，并经 SQL pairs 实测提升三率（§8.6 / §8.1）。
⇒ 优化后可重测验证三率提升，形成「治理前 → 治理后」的闭环证据。

### 8.5 优化动作实施记录（已实施，第三轮重测）
1. ✅ 修复测试脚本 #18 的 `Decimal` 序列化（`json.dumps(default=str)`）。
2. ✅ 为关键列补中文枚举描述（`updateModelMetadata`）——验证发现列描述只进 RAG 检索、**不约束字面量**，故进一步采用 SQL pairs。
3. ✅ 写入 20 条 **SQL pairs 黄金示例**（锁定口径 SQL：用 `public_*` 模型名、真实中文枚举、CASE WHEN 口径，避开引擎不认的 FILTER 方言），由 AI 服务建索引并作为 few-shot 注入 SQL 生成链路 → 治理后三率 90%。
4. ✅ 第三轮重跑 20 题，回填本表与测试清单。

### 8.6 治理后机制与遗留问题（第三轮）
原 §8.5 计划把 6 视图建模进 MDL，但落地实测确认 legacy/v1 **不支持把视图作为可检索模型**（建模 API 仅 `updateModelMetadata` 列描述 / 关系 / 视图收藏）。故选用 WrenAI **原生且真正进入生成链路**的机制——**SQL pairs 黄金示例**：
- 为 20 个核心问题各写一条锁定口径 golden SQL（中文枚举、CASE WHEN 口径）；
- 问数时按问题相似度检索并注入 few-shot，同时解决 (A) 口径锁定与 (B) 取值映射。

治理后 18/20 完全正确；**2 题瑕疵已定位根因（真实语义课题，非工具 bug）**：
- #4「开通养老账户的人有多少」：few-shot 借到 #3 渗透率 SQL，返回 0.4515 而非计数 4515 → **近义问法歧义**（#3/#4 过近）。
- #10「上个月赎回金额」：LLM 把"上个月"理解成日历月 2026-09（数据只到 2025-12）→ None → **相对时间语义**未采纳 golden SQL 的 `MAX(date)` 模板。

增强方向（作品集 next-step）：① 为易混问法补充 Instructions / 拆意图簇；② 加"时间锚点"规则（"上个月"= 数据最新月）；③ 升级到支持指标模型的 WrenAI 版本后再做标准指标化。

> 逐题原始结果见 `B项目_指标测试问题清单.md` 实测记录表与 `_20tests_result.json` / `_20tests_run3.log`。

## 9. 风险与边界

- 数据为合成，仅用于演示，不涉及真实用户隐私。
- 行级权限为设计项，未在本次 Demo 中接角色体系。
- WrenAI legacy/v1 分支为社区维护版本，生产需评估上游演进与 SLA。

## 10. 作品集叙事要点（给面试官的一句话）

> 我没有去卷「把 SQL 写对」，而是用 WrenAI 的语义层把养老业务的 6 个核心指标**口径锁死成视图**——这样无论谁问，答案口径都一致。过程中我还定位并解决了「WrenAI 要求 json_schema 而 DeepSeek 不支持」导致问答整体失败的关键坑，最终用国产百炼 Qwen 零成本跑通。
