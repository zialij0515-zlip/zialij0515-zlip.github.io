## 1. 产品概述

### 1.1 一句话定位
一款给个人使用的**减脂打卡与身体数据记录工具**：把「早/午/晚餐、运动、放纵餐」的每日记录，与体重、BMI、估算体脂率、热量收支汇成一张看得懂的首页，用低压力的方式帮助用户坚持。

### 1.2 要解决的问题
- 减脂类工具常把「记录」做成负担：食物库录入繁琐、热量计算门槛高，用户几天就弃用。
- 体重数字的短期波动容易引发焦虑，需要中性、可解释的呈现，而不是惩罚式反馈。
- 个人开发者没有后台运维能力，需要在微信云开发约束下做到「弱网可用、数据不串用户」。

### 1.3 产品原则
| 原则 | 落地方式 |
|---|---|
| 低摩擦优先 | 文字描述即自动估算热量；记录页进入时自动跳到当天第一个未打卡项 |
| 不羞辱、不焦虑 | 放纵餐用中性语言；文案如「身心愉快减脂哦，不准焦虑！」；估算值一律标注「仅供参考」 |
| 不假装医疗结论 | BMI / 体脂率 / 热量均为描述性估算，不给极端热量建议或医疗判断 |
| 离线可用 | 本地 Storage 为主路径，云端同步失败不影响本次记录成功 |
| 数据最小化 | 按 openid 隔离；不采集手机号；敏感信息仅存用户自己的记录 |

### 1.4 成功标准（产品假设，待数据验证）
用户能在**一次首次使用**中完成建档并看懂「今天下一步」；连续打卡天数随使用周数上升。验证口径见 `03-指标体系与埋点.md`。

## 2. 用户与场景

### 2.1 目标用户（产品假设，非调研结论）
| 画像 | 特征 | 核心诉求 |
|---|---|---|
| A · 轻量记录者 | 想减脂但不愿称重算卡路里，容易半途放弃 | 3 秒完成一次打卡，看到「我坚持了几天」 |
| B · 数据观察者 | 习惯记录体重，关心趋势而非单日数字 | 体重/BMI/体脂曲线、目标进度、周期性回看 |

### 2.2 典型场景
1. **早晨首次使用**：打开小程序 → 建档 → 首页看到今日四项待打卡。
2. **餐后随手记**：首页点「早餐」→ 自动进入记录页早餐 tab → 写「一拳米饭+鸡蛋」→ 实时看到估算热量 → 选心情、加图 → 保存。
3. **晚间复盘**：记录页填体重 → 首页看到今日总摄入/总消耗/基础代谢 → 数据页看趋势。
4. **达标时刻**：体重达到目标 → 生成海报存相册。
5. **想分享**：首页「今日打卡」右侧点分享 → 生成含打卡明细的卡片转发到聊天。

## 5. 信息架构

```
启动 → 是否已建档？
        ├─ 否 → onboarding（建档）
        └─ 是 → 首页（tab 0）
                 ├─ 记录（tab 1）
                 ├─ 数据（tab 2）
                 └─ 我的（tab 3）

非 tab 页面（navigateTo）
  ├─ poster        达标海报
  ├─ tipsList      减脂方法 / 运动推荐列表
  ├─ article       文章详情
  ├─ bmiGuide      BMI 科普
  ├─ bmrGuide      基础代谢 / 热量缺口科普
  └─ onboarding?from=profile  档案编辑（复用）
```

`app.json` 注册 10 个页面，TabBar 为自定义组件（`custom: true`），4 个 tab：首页 / 记录 / 数据 / 我的。

## 6. 核心流程

### 6.1 建档（R-A01 / R-A02）
1. 进入 `onboarding`；若 `onboardingComplete` 为真且非编辑模式 → 直接跳首页。
2. 填昵称（选填，默认「轻减小伙伴」）、性别、年龄、身高、起始体重、目标体重、目标日期、提醒开关。
3. 校验：年龄 / 身高 / 起始体重 / 目标体重必须能转成非零数字，否则 Toast「请补全有效的身体数据」。
4. 计算 `BMI`、`估算体脂率` → 写档案 + 写首条 `body_records`。
5. 异步同步云端（失败不阻塞）→ 跳首页。

### 6.2 餐食打卡（R-B01 / R-C01）
1. 首页点某餐卡片 → 写 `globalData.pendingRecordType` → `switchTab` 到记录页。
2. 记录页 `onShow` 读该值并 `loadType(type)`；无值且当前 tab 已打卡 → 按 `早→午→晚→放纵餐→运动` 找第一个未打卡项。
3. 输入文字 → 实时 `computeMealKcal`：空文本或「无/没吃/nothing」等否定词 → 0；否则走食物库估算并显示「饮食摄入 X 千卡」。
4. 选心情、最多选 3 张图 → 保存。
5. `addCheckin` 先按 `date+type` 去重 → 本地成功 → 上传图片 → `syncCheckin` 上云。

### 6.3 运动打卡（R-B03 / R-C04）
1. 切到运动 tab → 3 个大类手风琴（有氧默认展开）。
2. 勾选任意项，每项用 picker 选 0–120 分钟 → 实时显示「运动消耗 X 千卡」。
3. 保存校验：至少勾选一项，否则 Toast「请选择至少一项运动」。

### 6.4 体重记录（R-D01 / R-D02）
1. 记录页「数据更新」区输入体重，失焦即保存。
2. 若输入值 > 80，显示浅绿提示胶囊「可能是 130 斤？点我换成 65.0 kg」。
3. 有提示待处理时失焦**静默保存**（不弹 Toast）；用户点提示才换算、重算并弹一次结果。
4. 自动更新 BMI、估算体脂率、周完成率环形图。

### 6.5 分享（R-G01 / G02 / G03）
1. 首页 `refresh` 判断当天是否有打卡 → 有则预生成分享图并缓存。
2. 点「分享」→ `onShareAppMessage` 同步返回缓存图；无缓存则用 `promise` 异步生成，失败降级为纯文字转发。
3. 卡片不含头像昵称；放纵餐计入总摄入但不单独成行。

### 6.6 提醒（R-F06）
- **应用内（可靠）**：开启提醒 + 当天无打卡 + 本次未忽略 → 首页弹层；记录 tab 显示红点。
- **订阅消息（尽力而为）**：用户在「我的」开启或首页每日首次进入时请求授权 → 写 `reminder_subs` → 云函数每天北京时间 20:00 触发，跳过已关闭开关或当天已打卡的用户。
- **平台约束**：个人主体小程序默认仅「一次性订阅」，长期订阅需特定类目，减脂类基本拿不到；故不承诺每日必达。

## 7. 数据模型

### 7.1 本地 Storage（`utils/store.js`）
| Key | 结构 | 写入规则 |
|---|---|---|
| `slim_profile` | 档案对象 | 覆盖更新 |
| `slim_body_records` | 数组 `{ date, weight, bmi, bodyFat }` | 按 `date` 去重覆盖后按日期排序 |
| `slim_checkins` | 数组 `{ id, createdAt, date, type, mood, note, images, sportItems, kcal, kcalItems }` | 按 `date+type` 去重覆盖 |
| `slim_diary` | 数组 `{ id, date, text, createdAt, updatedAt }` | 按 `date` upsert |

### 7.2 云数据库（7 个集合）
| 集合 | 用途 | 权限 |
|---|---|---|
| `users` | 档案，文档 id = openid，`set` 幂等覆盖 | `_openid == auth.openid` |
| `body_records` | 身体数据 | 同上 |
| `checkins` | 打卡记录 | 同上 |
| `daily_summary` | 预留（当前代码未读写） | 同上 |
| `posters` | 预留（当前代码未读写） | 同上 |
| `diary` | 减脂日记 | 同上 |
| `reminder_subs` | 订阅授权 `{ templateId, authorizedAt }` | 同上；定时云函数以管理员权限读全表 |

### 7.3 云函数（3 个）
| 函数 | 职责 |
|---|---|
| `slim-login` | 返回调用方 `openid`（`cloud.getWXContext()`） |
| `slim-init` | 批量创建上述 7 个集合，已存在视为就绪 |
| `slim-reminder` | 定时触发（UTC 12:00 = 北京 20:00）；按授权用户逐一查开关与当日打卡，未打卡才发送订阅消息 |

### 7.4 云存储路径
- 打卡图片：`checkins/{openid}/{date}_{ts}_{idx}.jpg`
- 头像：`avatars/{openid}/{ts}.jpg`

## 9. 业务规则与算法（可直接作为测试用例依据）

| 编号 | 规则 | 公式 / 阈值 |
|---|---|---|
| BR-01 | BMI | `weight / (height/100)²`，保留 1 位小数 |
| BR-02 | BMI 分档 | `<18.5 偏低`；`<24 正常`；`<28 超重`；`≥28 肥胖` |
| BR-03 | 估算体脂率（Deurenberg） | `1.2×BMI + 0.23×age − 10.8×sex − 5.4`（sex：男 1 / 女 0），保留 1 位；**页面必须标注估算值·仅供参考** |
| BR-04 | 体脂分档 | 男 `<10 偏低 / ≤20 标准 / <25 偏高 / ≥25 肥胖`；女 `<20 偏低 / ≤30 标准 / <35 偏高 / ≥35 肥胖` |
| BR-05 | 基础代谢（Mifflin-St Jeor） | `10×weight + 6.25×height − 5×age + (男 5 / 女 −161)`，取整 |
| BR-06 | 分类×份量兜底估算 | 早 350 / 午 550 / 晚 480 / 放纵 650 / 运动 220；份量 `small .75 / normal 1 / large 1.35`（保留兼容，文字估算路径优先用食物库） |
| BR-07 | 食物文字估算 | 别名建索引 → **按关键词长度倒序**（长词优先，避免「鸡蛋」被「蛋」误命中）→ 已匹配字符区间去重 → 前向 6 字符取数量词 → `Σ(食物 kcal × 份数)` |
| BR-08 | 份量词 | `半=0.5`、`拳=1`、`大/多=1.5`、`小/少=0.6`、`口=0.2`，其次中文数字（一~十）、阿拉伯数字，默认 1 |
| BR-09 | 未命中兜底 | 无文字、全否定词、或食物库零命中 → 按餐次 `fallbackByType` 返回单条「默认估算」，`matched: false` |
| BR-10 | 运动消耗 | 22 项 MET 表每分钟 kcal（跑步 10、快走 5、HIIT 12、瑜伽 3…）× 分钟数，逐项四舍五入后累加；未选或 0 分钟不计 |
| BR-11 | 今日热量 | 摄入 = 所有非 `sport` 打卡 kcal 之和（含放纵餐）；消耗 = `sport` 打卡 kcal；净值 = 摄入 − 消耗 |
| BR-12 | 目标进度 | `(起始 − 当前) / (起始 − 目标) × 100`，裁剪到 0–100；起始=目标时返回 0 |
| BR-13 | 连续打卡 | 有打卡日期集合；今天未打卡则从**昨天**起算（避免白天误判为 0）；向前最多累加 365 天 |
| BR-14 | 周完成率 | 本周一 00:00 至周日 23:59:59；饮食天数 / 7、运动天数 / 7、体重记录天数 / 7，四舍五入 |
| BR-15 | 斤 → kg 提示 | `Number(value) > 80` → 提示 `(value/2).toFixed(1)`；**仅提示，用户点确认才换算** |
| BR-16 | 达标判定 | `当前体重 ≤ 目标体重` |
| BR-17 | 分享卡片 | 只列早/午/晚/运动四行；放纵餐计入总摄入不单独成行；缩略图最多 3 张，第 4 格显示「+N」；不含头像昵称；仅聊天转发 |
| BR-18 | 日记合并 | 按 `date` 去重，云端与本地比较 `updatedAt`，**新者胜出** |
| BR-19 | 云端合并 | 云端体重记录日期更新于本地最后一条时补写本地；当天云端打卡中本地缺失的 type 补写本地 |

> 食物库口径：171 条 / 9 类（主食 58、肉类 32、水产 23、蔬菜 12、蛋奶豆 11、汤 10、水果 10、零食 9、饮料 6）。数值为**估算值**，参考《中国食物成分表》及常见份量，不用于医疗或营养处方。

## 10. 异常态与边界

| 场景 | 期望表现 | 实现位置 |
|---|---|---|
| 云开发不可用 / 未初始化 | 全部功能走本地 Storage，Toast「已保存到本地」 | `cloud.enabled()` 分支 |
| 打卡同步云端失败 | 本地已保存，Toast「已本地保存，待同步」，不回滚、不阻塞 | `saveCheckin` catch |
| 图片上传失败 | 同上降级；图片保留本地临时路径 | `uploadImages` 异常上抛后被 catch |
| 重复保存同一天同一类型 | 本地按 `date+type` 覆盖，不产生第二条 | `store.addCheckin` |
| 同一天重复记体重 | 按 `date` 覆盖，不产生第二条 | `store.addBodyRecord` |
| 无身体数据 | 首页用 `startWeight` 兜底，数据页显示空态引导语 | `home.js` / `data.js` |
| 只有 1 条记录 | 折线图单点居中，不除零 | `data.js xOf` |
| 文字写「没吃 / 无 / nothing」 | 热量显示 0，但允许保存 | `computeMealKcal` |
| 运动勾选但分钟数为 0 | 该项不计入消耗；仍可保存 | `sportCalorie` filter |
| 当天无任何打卡 | 分享按钮灰置，点击给提示 | `onShareDisabledTap` |
| 分享图生成失败 | 降级为纯文字转发，不阻断 | `onShareAppMessage` promise catch |
| 用户关闭提醒开关 | 应用内不弹层；云函数跳过该用户 | `slim-reminder` 查 `users.remindCheckIn` |
| 用户当天已打卡 | 云函数跳过，不发订阅消息 | `slim-reminder` 查 `checkins` |
| 订阅消息未授权 / 配额用尽 | 不影响应用内提醒主路径 | 平台限制，见 6.6 |
| 跨设备首次进入 | 拉云端记录补齐本地 | `home.loadCloud` |

## 12. v1 明确不做的事

- **不做照片识别热量**：首版用「文字描述 + 食物库 + 份量」估算（见开发计划第 1 节已确认决策）。
- **不建完整食物数据库**：仅 171 条常见中餐条目 + 兜底估算，不追求营养学精度。
- **不绑定手机号**：只用微信 openid 识别用户。
- **不给医疗/营养处方**：所有数值为描述性估算，附「仅供参考」。
- **不做朋友圈分享**：只做聊天转发（`onShareAppMessage`）。
- **不承诺每日必达推送**：个人主体订阅消息受平台限制，主路径是应用内提醒。
- **不自建管理后台**：运营侧用云开发控制台 + `data-management-guide.html` 操作指南。

## 13. 静态检查发现的待验证风险

> 以下来自代码静态阅读，**尚未经真机/大数据量验证**，作为测试重点输入，不作为已确认缺陷结论。详见 `02-需求测试用例映射.md` 的「高风险专项」。

| 编号 | 风险点 | 依据 |
|---|---|---|
| RISK-01 | 日期使用 `new Date().toISOString().slice(0,10)`（UTC），北京时间 00:00–08:00 可能落到前一日；云函数已专门实现 `todayBeijing()` 做东八区换算，客户端未统一 | `store.js today()`、`home.js computeStreak/weekStartStr` |
| RISK-02 | 客户端 `db.collection().get()` 未设 `limit`，历史数据增长后可能读不全；云函数侧已加 `.limit(1000)` | `cloud.js getTodayCheckins/getCloudDiary/getLatestBodyRecord` |
| RISK-03 | 云端打卡/身体记录用 `add` 而非按业务键 upsert，本地去重但云端可能累积同日多条 | `cloud.js syncCheckin/syncBodyRecord` |
| RISK-04 | `parseQuantity` 固定向前看 6 个字符，多个食物紧邻时可能取到前一个食物的数量词 | `metrics.js` |
| RISK-05 | `daily_summary`、`posters` 两个集合已创建但代码未读写，属预留 | `slim-init/index.js` |
| RISK-06 | `profile.js testRemind()` 传 `test: true`，但 `slim-reminder/index.js` 的 `main` 未见对应分支 | 两处源码对照 |
| RISK-07 | 分享卡片 `imageUrl` 为本地临时路径，部分基础库版本可能不显示自定义图，已设计降级为纯文字 | `home.js onShareAppMessage` |
| RISK-08 | 周完成率用本地 `Date` 计算、日期字符串为 UTC 口径，跨时区/跨日边界可能与首页统计口径不一致 | `record.js computeWeekStats` 对照 `store.js today()` |
